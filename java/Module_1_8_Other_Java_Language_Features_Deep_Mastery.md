# 1.8.1 Nested Classes — Overview

A nested class is a class declared inside another class or interface.

Main categories:

```text
Nested Types
├── Static nested class
├── Inner member class
├── Local class
└── Anonymous class
```

Conceptually:

```text
Outer class
├── static nested class
├── inner member class
├── method
│   └── local class
└── anonymous class
```

Important distinction:

> A **static nested class is nested but is not an inner class** in Java terminology.

---

# 1.8.2 Static Nested Classes

## 1. What is it?

A static nested class is a class declared with `static` inside another class.

```java
class Outer {

    static class Nested {
        void print() {
            System.out.println("Hello");
        }
    }
}
```

Use:

```java
Outer.Nested nested = new Outer.Nested();
nested.print();
```

## 2. Why does Java have it?

It allows a type to be grouped logically with another type without requiring an enclosing object instance.

Good for:

- Builders
- Helper types
- Implementation details
- Related value types
- Encapsulated supporting classes

## 3. Internal Working

A static nested class does not require an `Outer` instance.

```text
Outer
  │
  └── Nested
        ↓
No implicit Outer object reference
```

This is a major difference from a non-static inner class.

## 4. Memory Behavior

A static nested class does not inherently hold a reference to an enclosing `Outer` instance.

This can avoid accidental retention of an outer object.

## 5. Access

A static nested class can access private members of its enclosing class, subject to Java's language access rules.

```java
class Outer {

    private static int value = 10;

    static class Nested {

        int getValue() {
            return value;
        }
    }
}
```

## 6. Common Mistakes

- [ ] Thinking static nested classes are top-level classes
- [ ] Thinking they require an outer instance
- [ ] Confusing static nested classes with inner classes

## 7. Production Use Cases

A classic example:

```java
public class User {

    private final String name;

    private User(Builder builder) {
        this.name = builder.name;
    }

    public static class Builder {

        private String name;

        public Builder name(String name) {
            this.name = name;
            return this;
        }

        public User build() {
            return new User(this);
        }
    }
}
```

## 8. Interview Questions

- [ ] Static nested class vs inner class?
- [ ] Does a static nested class have an outer object reference?
- [ ] Can a static nested class access private members of the outer class?

# 1.8.3 Inner Classes

## 1. What is it?

A non-static member class declared inside another class is an inner class.

```java
class Outer {

    private int value = 100;

    class Inner {

        void print() {
            System.out.println(value);
        }
    }
}
```

Create it:

```java
Outer outer = new Outer();
Outer.Inner inner = outer.new Inner();
```

## 2. Why?

Inner classes are useful when an object logically belongs to a specific enclosing object.

The inner instance can access the enclosing instance's members.

## 3. Internal Working

Conceptually:

```text
Outer instance
      ↑
implicit relationship
      │
Inner instance
```

The compiler/runtime representation involves an association with the enclosing instance.

You should understand the generated bytecode/fields when studying JVM internals.

## 4. `Outer.this`

An inner class can explicitly refer to its enclosing object:

```java
class Outer {

    class Inner {

        void printOuter() {
            System.out.println(Outer.this);
        }
    }
}
```

## 5. Memory Behavior

Because an inner object is associated with an outer object, retaining the inner object can retain the outer object.

This matters for:

- [ ] Long-lived callbacks
- [ ] Listeners
- [ ] Caches
- [ ] Threads
- [ ] Executors
- [ ] Application lifecycle

## 6. Common Mistakes

- [ ] Using inner classes when static nested classes are sufficient
- [ ] Accidentally retaining large outer objects
- [ ] Ignoring lifecycle implications

## 7. Production Guidance

Prefer a static nested class when the nested type does not logically need an outer instance.

# 1.8.4 Local Classes

## 1. What is it?

A local class is declared inside a method, constructor, initializer, or similar local scope.

```java
void process() {

    class Validator {

        boolean valid(String value) {
            return value != null && !value.isBlank();
        }
    }

    Validator validator = new Validator();

    System.out.println(validator.valid("Java"));
}
```

## 2. Why?

Local classes are useful for implementation details that are relevant only within a limited scope.

## 3. Scope

The class is visible only within the enclosing local scope.

```text
method
├── local class
└── local usage
```

## 4. Capturing Local Variables

A local/anonymous class can capture local variables that are final or effectively final.

```java
void greet(String name) {

    String message = "Hello " + name;

    class Greeter {
        void print() {
            System.out.println(message);
        }
    }

    new Greeter().print();
}
```

## 5. Important Runtime Concept

Captured local variables are not simply accessed as mutable stack variables after the method returns.

The compiler creates the required representation so the object can retain the captured value.

This connects to:

- [ ] Effectively final variables
- [ ] Object lifetime
- [ ] Lambda capture
- [ ] Heap allocation

## 6. Common Mistakes

- [ ] Trying to mutate captured local variables
- [ ] Creating unnecessarily complicated local classes
- [ ] Ignoring readability

## 7. Production Use

Use sparingly.

For reusable behavior, a top-level or nested type is often clearer.

# 1.8.5 Anonymous Classes

## 1. What is it?

An anonymous class is a class expression that declares and instantiates a class without giving it a conventional class name.

```java
Runnable task = new Runnable() {

    @Override
    public void run() {
        System.out.println("Running");
    }
};
```

## 2. Why?

Historically, anonymous classes provided concise one-off implementations.

They remain useful when:

- [ ] Extending a class for one use
- [ ] Implementing an interface with state
- [ ] Overriding multiple methods
- [ ] Needing a one-off subclass

## 3. Modern Java

For a functional interface, a lambda is usually simpler:

```java
Runnable task = () ->
        System.out.println("Running");
```

But an anonymous class can have its own fields, initializer blocks, and multiple methods.

## 4. Internal Working

The compiler generates a class representation for the anonymous class.

Study:

```text
source
 ↓
anonymous class
 ↓
compiler-generated class representation
 ↓
bytecode
```

Do not rely on old assumptions about exact generated class names; those are implementation details.

## 5. Memory Behavior

Like other objects, anonymous-class instances have normal object lifetime and can capture enclosing context.

For a non-static context, understand whether an enclosing instance is retained.

## 6. Common Mistakes

- [ ] Using anonymous classes where lambdas are clearer
- [ ] Creating large anonymous implementations
- [ ] Ignoring captured state

## 7. Production Use Cases

- Legacy callback APIs
- One-off class extension
- Framework hooks
- APIs requiring non-functional interfaces

# 1.8.7 Enums

## 1. What is it?

An enum defines a fixed set of named constants.

```java
enum Status {
    PENDING,
    PAID,
    CANCELLED
}
```

Usage:

```java
Status status = Status.PAID;
```

## 2. Why does Java have it?

Enums provide type-safe representation of a finite set of values.

Better than:

```java
String status = "PAID";
```

because arbitrary invalid strings can be supplied.

## 3. Basic Example

```java
enum PaymentStatus {

    PENDING,
    SUCCESS,
    FAILED
}
```

## 4. Enum Methods

Enums can contain fields, constructors, and methods.

```java
enum Priority {

    LOW(1),
    MEDIUM(2),
    HIGH(3);

    private final int level;

    Priority(int level) {
        this.level = level;
    }

    public int level() {
        return level;
    }
}
```

## 5. Enum Constructors

Enum constructors are not called directly by application code.

```java
Priority.HIGH
```

is an enum constant instance.

## 6. `values()` and `valueOf()`

```java
for (Priority priority : Priority.values()) {
    System.out.println(priority);
}
```

```java
Priority priority = Priority.valueOf("HIGH");
```

`valueOf()` throws `IllegalArgumentException` if the name does not match.

## 7. `ordinal()`

```java
Priority.HIGH.ordinal();
```

Avoid using `ordinal()` as a persistent business identifier.

If constants are reordered, ordinal values can change.

Bad:

```java
database.save(priority.ordinal());
```

Prefer an explicit stable code:

```java
enum Priority {

    LOW("L"),
    MEDIUM("M"),
    HIGH("H");

    private final String code;

    Priority(String code) {
        this.code = code;
    }
}
```

## 8. Enum Internals

Enum types are specialized Java types.

Every enum implicitly extends:

```java
java.lang.Enum
```

Enum constants behave as singleton instances within the enum type/class-loader context.

Understand:

- [ ] Generated enum methods
- [ ] `Enum.name()`
- [ ] `Enum.ordinal()`
- [ ] `Enum.valueOf()`
- [ ] Enum initialization
- [ ] Enum class initialization

## 9. Enum and Switch

```java
switch (status) {
    case PENDING -> ...
    case PAID -> ...
    case CANCELLED -> ...
}
```

Modern switch expressions and pattern matching make enum handling particularly expressive.

## 10. Common Mistakes

- [ ] Persisting ordinal values
- [ ] Comparing enum values with strings
- [ ] Creating huge enums containing unrelated behavior
- [ ] Ignoring unknown values at integration boundaries

## 11. Production Use Cases

- State machines
- Status values
- Categories
- Finite policies
- Feature modes
- Configuration choices

# 1.8.8 Annotations

## 1. What is it?

Annotations provide metadata that can be associated with program elements.

Examples:

```java
@Override
@Deprecated
@SuppressWarnings("unchecked")
```

## 2. Why?

Annotations allow tools, compilers, frameworks, and runtime code to associate metadata with:

- Classes
- Methods
- Fields
- Parameters
- Constructors
- Modules
- Packages
- Type uses

## 3. Basic Example

```java
@interface Audited {
}
```

Use:

```java
@Audited
class PaymentService {
}
```

## 4. Runtime Retention

Annotations can have different retention policies.

```java
@Retention(RetentionPolicy.RUNTIME)
@interface Audited {
}
```

Main policies:

```text
SOURCE
  ↓
Available to compiler/source tools

CLASS
  ↓
Stored in class file

RUNTIME
  ↓
Available through reflection
```

## 5. Target

```java
@Target(ElementType.METHOD)
@interface Audited {
}
```

Common targets:

- [ ] TYPE
- [ ] METHOD
- [ ] FIELD
- [ ] PARAMETER
- [ ] CONSTRUCTOR
- [ ] ANNOTATION_TYPE
- [ ] TYPE_USE
- [ ] RECORD_COMPONENT
- [ ] MODULE
- [ ] PACKAGE

## 6. Annotation with Members

```java
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
@interface Retry {

    int attempts() default 3;
}
```

Usage:

```java
@Retry(attempts = 5)
void process() {
}
```

## 7. Internal Working

For runtime annotations:

```text
Annotation declaration
       ↓
Compiler metadata
       ↓
Class file metadata
       ↓
Class loading
       ↓
Reflection
       ↓
Annotation API
```

Frameworks such as Spring heavily use annotation metadata.

## 8. Reflection

Example:

```java
Method method =
        PaymentService.class.getDeclaredMethod("process");

if (method.isAnnotationPresent(Retry.class)) {
    Retry retry = method.getAnnotation(Retry.class);
}
```

## 9. Common Mistakes

- [ ] Using runtime retention unnecessarily
- [ ] Putting business logic directly into annotations
- [ ] Overusing reflection
- [ ] Ignoring annotation inheritance rules
- [ ] Confusing metadata with executable behavior

## 10. Production Use Cases

- Spring dependency injection
- Validation
- REST mappings
- Serialization configuration
- Testing
- Security metadata
- ORM mappings

# 1.8.9 Varargs

## 1. What is it?

Varargs allow a method to accept a variable number of arguments.

```java
static int sum(int... numbers) {

    int total = 0;

    for (int number : numbers) {
        total += number;
    }

    return total;
}
```

Call:

```java
sum();
sum(1);
sum(1, 2, 3);
```

## 2. Syntax

```java
returnType method(Type... values)
```

The varargs parameter must be the final parameter.

```java
void log(String level, String... messages) {
}
```

## 3. Internal Working

Varargs are implemented using an array at the method boundary.

Conceptually:

```java
sum(1, 2, 3);
```

becomes approximately:

```java
sum(new int[]{1, 2, 3});
```

The exact compiler representation should be understood rather than assuming a textual rewrite.

## 4. Memory Behavior

Calling a varargs method may require an array allocation.

This matters in:

- [ ] Hot loops
- [ ] High-throughput code
- [ ] Allocation-sensitive paths

The JVM may optimize allocations in some circumstances, but do not assume it will always eliminate them.

## 5. Varargs + Overloading

Be careful:

```java
void process(Object value) {}
void process(Object... values) {}
```

Overload resolution can produce surprising results.

## 6. `null` Edge Case

Varargs can be called with an explicit array:

```java
process((String[]) null);
```

This differs from:

```java
process();
```

Inside the method:

```java
values == null
```

may be true in the first case.

## 7. Generic Varargs

Generic varargs can produce heap-pollution warnings.

Example:

```java
static <T> void printAll(T... values) {
}
```

Understand:

- [ ] Non-reifiable types
- [ ] Heap pollution
- [ ] `@SafeVarargs`
- [ ] Why `@SafeVarargs` must only be used when the implementation is actually safe

## 8. Common Mistakes

- [ ] Forgetting the final-parameter rule
- [ ] Assuming zero arguments means null
- [ ] Ignoring allocation cost
- [ ] Unsafe generic varargs
- [ ] Overloading varargs excessively

## 9. Production Use Cases

Good for APIs such as:

```java
String.format(...)
List.of(...)
Set.of(...)
```

and custom convenience APIs.

# 1.8.10 Java Is Always Pass-by-Value

## 1. What is it?

Java is **always pass-by-value**.

For primitives:

```java
int x = 10;
change(x);
```

the value `10` is copied.

For object references:

```java
User user = new User();
change(user);
```

the **reference value** is copied.

Java does not pass object references by reference in the C++ `reference` sense.

## 2. Primitive Example

```java
static void change(int x) {
    x = 100;
}

int value = 10;

change(value);

System.out.println(value); // 10
```

The method receives a copy.

## 3. Reference Example

```java
static void change(User user) {
    user.setName("Bob");
}
```

If:

```java
User user = new User("Alice");

change(user);
```

the copied reference still points to the same object.

Therefore:

```text
Caller variable
      ↓
  reference A
      ↓
   User object

Method parameter
      ↓
  copied reference A
      ↓
   same User object
```

Mutation is visible because both reference values point to the same object.

## 4. Reassignment Example

```java
static void change(User user) {
    user = new User("Bob");
}
```

The caller's reference does not change.

```text
Caller reference
      ↓
Object A

Method parameter
      ↓
Object A

parameter = Object B

Caller
      ↓
still Object A
```

## 5. The Best Mental Model

Always ask:

> What value was copied into the parameter?

For an object parameter:

> The value of the reference was copied.

Not:

> The object itself was copied.

And not:

> Java passes objects by reference.

## 6. Edge Cases

- [ ] Primitive mutation
- [ ] Object mutation
- [ ] Reference reassignment
- [ ] Arrays
- [ ] Collections
- [ ] `final` parameters
- [ ] Mutable vs immutable objects
- [ ] Null references

## 7. Production Importance

This affects:

- API design
- Mutability
- Defensive copying
- Thread safety
- Collection behavior
- Debugging
- Method contracts

# 1.8.11 Java Reference Semantics

## 1. What is a Reference?

An object variable does not contain the object itself in the Java language model.

```java
User user;
```

The variable holds a reference value that can identify/access an object.

Avoid depending on a specific physical JVM representation such as a raw machine pointer.

## 2. Aliasing

Two references can refer to the same object.

```java
User a = new User("Alice");

User b = a;
```

Now:

```text
a ─────┐
       ↓
     User
       ↑
b ─────┘
```

Mutation through one reference is observable through the other.

## 3. Null

```java
User user = null;
```

The variable does not refer to an object.

Calling:

```java
user.getName();
```

causes a `NullPointerException`.

## 4. Object Identity

Two objects can contain equal data but have different identities.

```java
User a = new User("Alice");
User b = new User("Alice");
```

Usually:

```text
a != b
```

because they are distinct object instances.

Whether `a.equals(b)` is true depends on the class's equality contract.

## 5. Reference Copying

```java
User b = a;
```

does not clone `a`.

It copies the reference value.

## 6. Arrays

Arrays are objects.

```java
int[] a = {1, 2, 3};
int[] b = a;
```

Both references point to the same array.

## 7. Garbage Collection Connection

An object becomes eligible for garbage collection when it is no longer reachable through the relevant GC roots and references.

Conceptually:

```text
GC Root
  ↓
Object A
  ↓
Object B
```

If the root no longer reaches A, the reachable subgraph may become collectible.

Understanding references is therefore essential to understanding:

- [ ] Memory leaks
- [ ] Static references
- [ ] ThreadLocal retention
- [ ] Caches
- [ ] Object graphs

# 1.8.12 `==` vs `equals()`

## 1. What is `==`?

For primitive operands, `==` compares values.

```java
int a = 10;
int b = 10;

a == b; // true
```

For reference operands, `==` compares whether the references identify the same object.

```java
User a = new User("Alice");
User b = new User("Alice");

a == b; // false
```

## 2. What is `equals()`?

`equals()` is a method inherited from `Object` that is intended to define logical equality according to the class contract.

```java
a.equals(b);
```

The default implementation from `Object` is identity-based.

Classes such as `String` override it.

```java
new String("Java").equals(new String("Java")); // true
```

## 3. Comparison

```text
==

Primitive
  ↓
Value comparison

Reference
  ↓
Same object/reference identity


equals()

Object
  ↓
Logical equality according to implementation
```

## 4. Null

This can throw:

```java
user.equals(other);
```

if `user == null`.

Safer when appropriate:

```java
Objects.equals(user, other);
```

## 5. String Pool Example

```java
String a = "Java";
String b = "Java";

a == b;       // commonly true because literals are interned
a.equals(b);  // true
```

Do not use `==` to test string content.

Correct:

```java
a.equals(b)
```

or:

```java
Objects.equals(a, b)
```

## 6. Wrapper Edge Cases

Do not rely on identity comparisons for boxed values.

```java
Integer a = 100;
Integer b = 100;

a == b;
```

may be true because of caching.

But:

```java
Integer x = 1000;
Integer y = 1000;

x == y;
```

should not be used as a value comparison.

Use:

```java
Objects.equals(x, y);
```

or unbox deliberately when appropriate.

## 7. `equals()` Contract

Master:

### Reflexive

```text
x.equals(x) == true
```

### Symmetric

```text
x.equals(y) == y.equals(x)
```

### Transitive

```text
x.equals(y)
y.equals(z)
→ x.equals(z)
```

### Consistent

Repeated calls should remain consistent when relevant state has not changed.

### Non-null

```text
x.equals(null) == false
```

for a well-designed implementation.

## 8. `equals()` and `hashCode()`

If:

```java
a.equals(b)
```

is true, then:

```java
a.hashCode() == b.hashCode()
```

must be true.

The reverse is not required.

This is critical for:

```text
HashMap
HashSet
ConcurrentHashMap
```

## 9. Common Mistakes

- [ ] Using `==` for String content
- [ ] Using reference identity when logical equality is required
- [ ] Overriding equals without hashCode
- [ ] Including mutable fields carelessly
- [ ] Breaking symmetry through inheritance
- [ ] Calling equals on a possibly null reference

# 1.8.13 Equality and Identity Deep Dive

Understand these separate concepts:

```text
Identity
   ↓
Are these the same object?

Equality
   ↓
Should these objects be considered equivalent?
```

Example:

```java
Money a = new Money("100");
Money b = new Money("100");
```

Potentially:

```text
a == b       → false
a.equals(b)  → true
```

depending on the implementation.

## Identity API

Study:

```java
System.identityHashCode(object);
```

Important:

> `identityHashCode()` is about object identity, not the object's overridden `hashCode()` contract.

# 1.8.21 Production Debugging Checklist

## Equality Bug

```text
1. Check == vs equals()
2. Check null
3. Check equals contract
4. Check hashCode contract
5. Check mutable fields
6. Check inheritance
7. Check collection behavior
```

## Reference Bug

```text
1. Identify aliases
2. Check who owns the object
3. Check mutations
4. Check reassignment
5. Check defensive copying
6. Check lifecycle
```

## Memory Retention

```text
1. Identify GC roots
2. Follow reference chain
3. Check inner classes
4. Check anonymous callbacks
5. Check static fields
6. Check ThreadLocal
7. Check caches
```

## Annotation Bug

```text
1. Check retention policy
2. Check target
3. Check annotation declaration
4. Check class loading
5. Check reflection lookup
6. Check annotation processor/framework scanning
```
